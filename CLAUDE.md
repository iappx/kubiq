## Versioning and releases

**The `VERSION` file at the root is the version.** Nine build files repeat it — `build/config.yml`, `build/windows/info.json`, `build/windows/nsis/wails_tools.nsh`, `build/windows/wails.exe.manifest`, both MSIX manifests, `build/linux/nfpm/nfpm.yaml`, `frontend/package.json` and its lock file.

- **Never edit a version by hand, in any of those files.** Change `VERSION` alone: `.githooks/pre-commit` writes the number into the other nine and adds them to the same commit, so the two can never be committed apart. `wails3 task setup:hooks` installs the hook, once per clone.
- Outside a commit the same job is `bash .github/scripts/version.sh set <major.minor.patch>`, and `bash .github/scripts/version.sh check` verifies the files and fails CI when they disagree. A new file that carries the version is added to the `targets` list at the top of that script.
- A version is three numbers. Suffixes (`-rc.1`) are rejected: the MSIX manifests cannot express them.
- **Pushing a changed `VERSION` to `main` publishes a release.** `.github/workflows/release.yml` builds Windows and Linux, attaches the artifacts to a draft release, and publishing that draft creates the `v<VERSION>` tag.

### Every commit bumps the version

**Every commit raises `VERSION`, following semver.** Whoever prepares a change raises the number in the same working tree, so the change and its version are committed together — the owner commits, the bump is already there.

| Part | When | Example |
|---|---|---|
| **patch** | fixes, refactoring, tests, documentation, build and CI changes — nothing a user can newly do | `0.2.0 → 0.2.1` |
| **minor** | a new feature or a visible change in behaviour; patch resets to zero | `0.2.1 → 0.3.0` |
| **major** | **only when the repository owner explicitly asks for it** in that request; minor and patch reset to zero | `0.3.0 → 1.0.0` |

- **Never raise major on your own judgement.** A change that looks breaking still gets minor — raise the question in the summary instead.
- **One bump per commit, counted from the version in `HEAD`.** A working tree that already carries a bump over `HEAD` is not bumped again; if the pending change has grown from a fix into a feature, turn the patch bump into a minor one.
- Change `VERSION` alone, as above — the hook carries the number into the other nine files at commit time.
- Because a changed `VERSION` on `main` publishes a release, every commit that reaches `main` becomes a release.

## Go backend — rules (`core/`, `main.go`)

- A service bound into the frontend is a plain struct with exported methods in its own package under `core/services/{name}/`. Register it in the `Services` list in `main.go`.
- Method signatures are the frontend's API surface: use plain types and structs the binding generator can express. Return a result struct (see `io.IOResult`) rather than an `error` where the frontend needs to branch on failure.
- Types shared by a service live in `types.go` next to it; OS-specific code goes in `{name}_windows.go` / `{name}_linux.go` behind build tags.
- Relative paths are resolved against the executable, not the working directory — always go through `utils.GetPath`.
- After changing any bound signature, run `task bindings` and leave the regenerated files in the working tree (committing is the owner's call).

### The Go side is a thin client — data belongs to the frontend

**Every external interaction — HTTP APIs, databases, sockets, anything — is a dumb client in Go and everything else in the frontend.**

A bound service is generic: it performs the mechanical act and knows nothing about the data passing through it.

- **HTTP.** Go exposes something like `Send(request) HttpResult` where method, URL, headers and body all come from the caller. The Go side knows no endpoints, no base URL, no auth scheme beyond passing a header it was handed, and never inspects a payload.
- **Databases.** Go opens the connection and runs what it is given — statement plus parameters in, rows out. No table names, no queries, no mapping written in Go.
- **Files.** `IoService` is already this shape and is the reference to copy: a path and options in, a result struct out.

What stays in the frontend: which endpoint or query, what the payload looks like, how the answer maps onto entities, retries, validation, and the meaning of a failure. It reaches all of it through an entity-repo transport (see **Data**), so the Go client is just what that transport calls.

Why this way:

- Data rules live in exactly one place instead of being split across two languages.
- Adding an endpoint or a query is a frontend change — no rebuild of the binary, no `task bindings`.
- The Go layer stays small enough to be obviously correct, and the frontend stays testable by faking a transport.
- Both halves run on the user's machine, so pushing logic into Go buys no secrecy — only a second place to maintain it.

Go still reports failure as data (`{ success, data }` result structs, per the rule above); the frontend transport turns it into an `ApiError`.

❌ A bound method named after a domain operation (`FetchUserOrders`, `SaveInvoice`), an endpoint or SQL string compiled into Go, a struct in Go mirroring a domain entity.

## Architecture — layers

Layers at the top level, feature folders inside each. Dependencies point **inwards only**: `presentation → application → domain`, and `application → infrastructure → domain`.

```
src/
  domain/                      entities, events, errors, pure helpers — no Vue, no DI, no IO
    entities/{feature}/         entity-repo entities + catalogues + types/
    events/{area}/              one event class per file
    errors/                     ApiError
    models/                     models that are not entities (MenuItem, AppTheme)
  application/
    services/{domain}/         one folder per service — the class and everything it owns
    handlers/                  event subscribers that perform side-effects
    validators/                form draft validators
  infrastructure/
    entityRepo/                context, transports, queries
    eventBus/                  EventBus (mitt-backed)
    wails/                     WailsRuntimeService
    theme/                     ThemeAdapter
  store/ views/ components/ containers/   presentation (Pinia stores, pages, components)
  config/ constants/ lib/      environment, DI tokens, framework infrastructure
```

**There is no `src/services/` at the root of `src/`.** A service is application code and lives under
`application/services/`; the event bus is infrastructure and lives under `infrastructure/`. A folder
named `services/` anywhere other than `application/` is a defect — the top level of `src/` is the
layer list above and nothing else.

**`domain` depends on nothing** except two allowed libraries — `@iappx/entity-repo` (plain decorators and a base class, no IO) and, where the project uses it, `@iappx/entity-repo-query` for named filter rules (a builder over plain data, no IO). No Vue, no tsyringe, no bindings, no reaching outside.

### In MVVM terms

| MVVM | What it is here | What it may not do |
|---|---|---|
| Model | `domain/`, `application/`, `infrastructure/` | know about Vue or stores |
| ViewModel | stores in `store/modules/**` and component classes | depend on anything but `application/`; touch repositories, `localStorage`, `document`, timers |
| View | `<template>` in `.vue` | hold logic — bindings and `$emit` only |

**A store never reaches into `infrastructure` directly.** An application service always sits between them. The one place a store awaits IO is loading its collection (see **Stores**).

## Data — through `@iappx/entity-repo` only

**Storing and reading a collection follows the entity-repo conventions — always.** It does not matter where the data lives: a file next to the binary, `localStorage`, an HTTP API, a Wails binding, a database. The shape is always the same:

```
entity (domain/entities)  →  set on a context (@RepoEntitySet)  →  query  →  transport  →  the outside world
```

Calling `fetch`, `axios`, `localStorage`, the bindings or the file system directly from a service, a store or a component is forbidden.

**A single value is the exception.** A UI preference or a lone record with no collection behind it (the colour theme, whether the sidebar is collapsed) may live in an adapter under `infrastructure/` — see `ThemeAdapter`. Modelling it as an entity is allowed but not required. As soon as there are many of them and they form a list, it is a collection and the rule above applies with no exemptions.

### Pick the package before writing any plumbing

`@iappx/entity-repo` is the core of a family, and the dialect packages already contain exactly what is tempting to hand-roll: filter encoding, query strings, GraphQL documents, paging, selection, payload building, response reading. **If the source matches a package, that package is used. Writing an equivalent by hand is a defect, however small it looks.**

| Package | Use it for | What it gives |
|---|---|---|
| `@iappx/entity-repo` | always — the core | `RepoEntityBase`, `@RepoEntityField`, `EntityContextBase`, `@RepoEntitySet`, `EntityQuery`, `ITransport` / `IStreamTransport` |
| `@iappx/entity-repo-query` | every query that filters, sorts, pages or selects | the typed builder, the query AST, `QueryableEntityQuery`, `QueryValidator`, `CompileContext` |
| `@iappx/entity-repo-rest` | an HTTP / REST API | `RestEntityQuery` (`getAll` `getOne` `getPage` `count` `create` `update` `patch` `delete` `updateMany` `deleteMany`), `FetchTransport`, swappable encoders for url, filters, order, paging, response |
| `@iappx/entity-repo-gql` | a GraphQL API | `GqlEntityQuery` (the same methods plus `watch()` subscriptions), `FetchGqlTransport`, strategies for any schema convention — no schema, no codegen |
| `@iappx/gql-builder` | building GraphQL documents at runtime outside the gql dialect | `Gql`, `GqlField`, `GqlOperation` |

Anything with no dialect — a database, a socket, a file, `localStorage` — gets an `ITransport` (or `IStreamTransport`) plus a query class of our own, exactly as the `FileSystemTransport` / `FileEntityQuery` pair here does. **That is the only case in which query code is written by hand**, and it still extends `QueryableEntityQuery` and compiles the AST rather than inventing a vocabulary of its own.

- The transport is where the choice of plumbing lives, not the layers above it. A REST or GraphQL source that must go through Go (see **The Go side is a thin client**) keeps the dialect unchanged: the transport implements `ITransport<TRestRequest>` / `ITransport<TGqlRequest>` and calls the dumb Go client instead of `fetch`.
- ❌ A hand-written `fetch`/`axios` repository, a query-string builder, a `filter[0][field]=` encoder, a GraphQL document in a template literal, `graphql` / `@apollo/client` / `urql` as the data layer, generated API clients.
- **Read the package README before using it** (npm / github.com/iappx). Each covers far more than this section — every default is replaceable and the answer is usually an option, not a subclass.
- Adding one of these packages is a dependency change and needs the repository owner's approval (see **Third-party libraries**), and it comes with peers: `entity-repo-query` requires `@iappx/entity-repo` ≥ 3.2.0 — which the pinned core already satisfies — `entity-repo-rest` adds `entity-repo-query`, and `entity-repo-gql` adds `gql-builder` on top.

### Queries go through the builder

Everything past "give me all of it" is expressed with the typed builder of `@iappx/entity-repo-query`, on the entity set itself:

```ts
public getRecent(from: string): Promise<TPage<AccountEntity>> {
    return this.repoProvider.context.accounts
        .where(f => f.and(f.eq('status', 'active'), f.gte('createdAt', from)))
        .orderBy('createdAt', 'desc')
        .take(20)
        .getPage()
}
```

- **Filtering, sorting and paging belong in the query.** ❌ `getAll()` followed by `.filter()`, `.sort()` or `.slice()` in a service, a store or a component — that is a query written in the wrong place, and it drags the whole collection over the wire to do it.
- A recurring condition is a **named business rule**: a static method returning a filter node, kept next to the entity (`AccountFilters.active(f)`) and reused by every query — not a chain copied around.
- Builders are immutable and an entity set hands out a fresh query on every access, so a prepared query is safe to share and to branch.
- Field sets come from `select` / `include` / `exclude`, not from fetching everything and picking afterwards.
- **Writes go through the entity**: `create` / `update` / `patch` / `delete` serialise with `entity.serialize(...)`, so `isReadonly`, `isGenerated`, `isClientOnly` and change tracking are already handled. ❌ Assembling a request body by hand.
- What the backend spells differently is a **strategy, not a fork**: plug an encoder or compiler into the entity set options (REST — `IFilterEncoder`, `IUrlBuilder`, `IRequestFactory`, `IResponseAdapter`, `IRequestMiddleware`; GraphQL — `IOperationNaming`, `IFilterCompiler`, `IArgumentStrategy`, `ISelectionCompiler`, `IVariableStrategy`). Each declares its capability slice, and `QueryValidator` rejects a query the backend cannot express **before** the request leaves the process.
- Before subclassing anything, use the escape hatches: `rawFilter`, `withMeta`, and — on REST — `withQueryParams`, `withHeaders`, `withPathParams`, `withSignal`, `rawRequest`.
- A query class of our own for a source with no dialect implements `IQueryCompiler` and declares its capabilities: it receives the same AST every dialect receives, so the calling code does not change if the source later moves to REST or GraphQL.

### A hand-written query compiles the AST — it does not invent a vocabulary

**The moment a source can filter, sort, page or select, `@iappx/entity-repo-query` is how those are expressed — including when you are writing the query class yourself.** Writing the class by hand buys you a compiler for one source, never a second query language.

This is the rule that gets broken quietly, because a bespoke API looks reasonable in isolation. A SQL, IndexedDB or socket source that can genuinely filter and sort must extend `QueryableEntityQuery`, implement `IQueryCompiler`, and declare its capability slice — then `where` / `orderBy` / `take` / `skip` / `select` arrive as the same AST every dialect receives, and `QueryValidator` rejects what the source cannot express before a request is built.

```ts
// ❌ a second query language: the caller now speaks SQL-shaped options that exist
//    nowhere else, and every consumer is welded to this one source
export class SqlEntityQuery<T> extends EntityQuery<T, SqliteTransport> {
    select(options: { where?: { field: string; operator: '=' | '>'; value: unknown }[]
                      orderBy?: { field: string; direction: 'asc' | 'desc' }[]
                      limit?: number }): Promise<T[]>
}
store.select({ where: [{ field: 'isRead', operator: '=', value: false }], limit: 20 })

// ✅ the source compiles the shared AST; the call site is identical to REST and GraphQL
export class SqlEntityQuery<T> extends QueryableEntityQuery<T, SqliteTransport> implements IQueryCompiler {
    // capabilities: filter, order, paging offset — declared, so QueryValidator can enforce them
}
context.notifications.where(f => f.eq('isRead', false)).orderBy('id', 'desc').take(20).getAll()
```

Why this matters more than it looks: the AST is the contract that makes the storage decision reversible. Callers written against it survive the source moving to REST, to GraphQL, or to a different local store — callers written against a bespoke options object have to be rewritten, and until they are, nobody can tell which of them rely on quirks of the one implementation.

**The exception is a source that genuinely cannot select** — a JSON blob read whole from a file or `localStorage`, where "filtering" would mean loading everything and filtering in memory anyway. `JsonCollectionQueryBase` and its `FileEntityQuery` / `LocalStorageEntityQuery` descendants are that case, and they deliberately expose only `getAll` / `getById` / `create` / `update` / `remove` with no builder. Do not copy that shape onto a source that can do better: a database can, and modelling it as a dumb blob throws away the reason to use a database at all.

### Entity

```ts
export class ItemEntity extends RepoEntityBase<ItemEntity> {
    @RepoEntityField({ isPrimaryKey: true })
    id: string

    @RepoEntityField()
    title: string
}
```

1. File `{Name}Entity.ts` under `domain/entities/{feature}/`, class name matching the file. **The `Entity` suffix is mandatory.**
2. Exactly one field carries `isPrimaryKey: true`.
3. Fields have **no initialisers**: `@RepoEntityField` replaces them with accessors on the prototype.
4. **Entities are mutable** — no `readonly`, no `withChanges`. Fields are changed in a service or a query; presentation receives the result of an operation instead of editing an entity in place.
5. **Serialise through `getDataValues()`** and build through `Entity.build(data)`. `JSON.stringify(entity)` yields the object's internals, not its data.
6. **Entities never extend one another** — the field map lives on the prototype, so a subclass would write its fields into its parent's map.
7. Nested entities go through `@RepoEntityField({ nestedType: () => Other })`.
8. `useDefineForClassFields: false` in `tsconfig.json` and `vitest.config.ts` is mandatory: with `true`, field declarations wipe the accessors.

Value catalogues (`ItemStatusCatalog`), scalar types (`TItemStatus`) and form drafts (`TItemDraft`) live next to the entity and are re-exported from that folder's `index.ts`.

### Transport

A transport implements `ITransport<TParams>` with a single `send` method. **It is the only place where external IO is allowed**, and the only place that imports `bindings/`.

Two ship with the template:

| Transport | Params | Reaches |
|---|---|---|
| `FileSystemTransport` | `TFileRequest` (`path`, `operation`, `content?`) | Go `IoService` binding — a file next to the binary |
| `LocalStorageTransport` | `TLocalStorageRequest` (`key`, `operation`, `content?`) | browser `localStorage` |

- The params type is a `T{Name}Request` of its own under `transport/types/`.
- Any failure becomes an `ApiError` (see **Errors**). `LocalStorageTransport` treats a rejected write — quota, privacy mode — as one, because from that point on what the user sees is not what is stored.
- An unavailable environment is not a failure: `FileSystemTransport` checks `WailsRuntimeService.isAvailable()` and `LocalStorageTransport` checks that `localStorage` exists. In a browser, in tests and under a bare `vite` there are no bindings — a transport degrades, it does not throw.
- A new data source (HTTP, a database) means a new transport next to these, never a `fetch` inside a service. For REST and GraphQL the transport is the one that ships with the dialect (`FetchTransport`, `FetchGqlTransport`) or a class of ours implementing the same `ITransport<TRestRequest>` / `ITransport<TGqlRequest>` — not a transport with a request shape invented here. If it needs the Go side, that side stays a dumb client and the transport keeps the knowledge — see **The Go side is a thin client**.

### Query

A query says how a transport turns into entities, and may act as a builder (methods returning `this`).

`JsonCollectionQueryBase` holds the logic shared by every "collection as a JSON array" source — CRUD, parsing, dropping rows without a primary key. A concrete query only says how to read and write the blob:

```ts
export class FileEntityQuery<T extends RepoEntityBase>
    extends JsonCollectionQueryBase<T, FileSystemTransport, TFileQueryOptions> {

    protected read(): Promise<string | null> {
        return this.transport.send<string | null>({ path: this.file, operation: 'read' })
    }

    protected async write(content: string): Promise<void> {
        await this.transport.send<null>({ path: this.file, operation: 'write', content })
    }
}
```

`LocalStorageEntityQuery` is the same class against `LocalStorageTransport`, keyed by `key` instead of `path`. Both expose `getAll`, `getById`, `create`, `update`, `remove`.

- One query class per way of reaching data, not per entity: `FileEntityQuery` serves any collection kept in a JSON file.
- Set options (`{ file: 'data/items.json' }`, `{ key: 'items' }`) are a `T{Name}Options` type under `queries/types/`.
- A missing or empty source is an empty collection, not a failure. Corrupted data is an `ApiError`.
- Entities are built with `this.entityConstructor.build(...)`; rows without a primary key are dropped.
- A source that is not a JSON array is never a subclass of the JSON one. A REST or GraphQL source takes `RestEntityQuery` / `GqlEntityQuery` from its dialect package; anything else gets a query class of its own — see **Pick the package before writing any plumbing**.

### Context

```ts
export class AppEntityContext extends EntityContextBase<FileSystemTransport> {
    @RepoEntitySet(() => ItemEntity, () => FileEntityQuery, { file: 'data/items.json' })
    public items: FileEntityQuery<ItemEntity>
}
```

- Adding a collection means adding a property here. Services never construct a query or touch a transport.
- **A context is typed by one transport.** A second source means a second context next to it, not a mix:

```ts
export class LocalEntityContext extends EntityContextBase<LocalStorageTransport> {
    @RepoEntitySet(() => DraftEntity, () => LocalStorageEntityQuery, { key: 'drafts' })
    public drafts: LocalStorageEntityQuery<DraftEntity>
}
```

- A set property hands out a **new query on every access**; builder state does not survive between accesses.

### Reaching the context from the app

`EntityRepo.getContext()` builds a new context on every call, so it is built once in `EntityRepoProvider` (`@singleton`). Services inject the provider and read `context`:

```ts
public getAll(): Promise<ItemEntity[]> {
    return this.repoProvider.context.items.getAll()
}
```

A second context is registered in the same provider — `EntityRepo.create().use(AppEntityContext, fileTransport).use(LocalEntityContext, localStorageTransport)` — and exposed through an accessor of its own.

## Errors

**Any failure to reach data is a business error, and the user gets told.** A blank screen with no explanation is worse than an error message.

1. **The API layer writes the text.** A transport throws `ApiError(message, details)`, where `message` is what the user reads and `details` is the technical part. Callers up the stack decide whether they can recover, never how the failure reads.
2. **It travels up as an event.** Whoever catches it and cannot deal with it emits `AppErrorEvent(error, context)`. This is the one event allowed to cross every layer bottom-up.
3. **One handler decides.** `ErrorHandler` shows an `ApiError` as a toast; anything else is a defect in our own code and goes to `console.error` — the user is not interrupted with what they cannot fix.
4. **Environment is not an error.** A missing Wails runtime, an absent file on first run and the like are handled quietly.
5. **A store action that reaches for data does not throw outwards**: it catches and emits `AppErrorEvent` (see `ItemStore.guard`).
6. Uncaught `unhandledrejection` and `window.error` are picked up in `AppBootstrap` and end up in the same place.

## Events

### When an event, when a plain call

The bus is not a way to connect anything to anything. An event is justified in exactly three cases:

1. **There is more than one consumer** — or there plainly will be.
2. **It crosses layers bottom-up** — typically errors (`AppErrorEvent`).
3. **The sender must not know the receiver** — a store changes state without having to know that something persists it or raises a toast.

Everywhere else, with one known consumer, use a **plain call on an injected service**. Inside a single component, props/`$emit` and direct method calls remain the right tool; the bus is for domain changes and their cross-cutting consequences.

### Event class

```ts
export class ItemCreatedEvent {
    constructor(
        public readonly id: string,
        public readonly title: string,
    ) {}
}
```

- One class per file under `domain/events/{area}/`, file named after the class.
- Fields are `public readonly` constructor parameters, primitives preferred; an entity is allowed when the receiver needs the whole object.
- Identity comes from `TypeIdentity` (a WeakMap keyed by the class object) — no registration needed. **A subclass gets an identity of its own** and never reaches handlers of its base.

### Handlers (`application/handlers/`)

Cross-cutting consequences of domain events live in handler classes, not in stores:

```ts
@singleton()
export class ItemNotificationHandler {
    constructor(
        @inject(EventBus) private readonly eventBus: EventBus,
        @inject(ToastService) private readonly toastService: ToastService,
    ) {
        this.eventBus.registerHandler(ItemCreatedEvent, e => this.toastService.success(`Record "${e.title}" created`))
    }
}
```

- The file is `{Name}Handler.ts` — **the suffix is mandatory**: handlers are wired by `import.meta.glob('./application/handlers/**/*Handler.ts')` in `AppBootstrap`. There is no manual list; a file with another suffix is never found, never constructed, and its subscriptions silently never happen.
- A handler is a `@singleton()` and registers its subscriptions in its constructor.
- Domain handlers live in their feature's subfolder (`handlers/items/`), shared ones at the root of `handlers/`. **A shared handler must not know a single feature** — otherwise deleting a domain turns into editing shared code.
- A handler may push results into a store through a narrow setter — that is the only allowed handler→store coupling.

### Subscribing outside a handler

In a component: register in `created()` and **unregister in `beforeUnmount()`**. `EventBus.unregisterHandler` removes a subscription by function reference, so the handler is kept in a class field — but the arrow is **built inside `created()`**, never as a field initialiser:

```ts
private onCreateRequested!: () => void

created(): void {
    this.onCreateRequested = () => this.openCreate()
    this.eventBus.registerHandler(OpenItemCreateModalEvent, this.onCreateRequested)
}

beforeUnmount(): void {
    this.eventBus.unregisterHandler(OpenItemCreateModalEvent, this.onCreateRequested)
}
```

**Why not a field initialiser.** `@iappx/vue-facing-di` resolves the class once, copies its own fields into the component's reactive state and then drives everything through Vue's proxy. Hooks and methods run on that proxy, but a field initialiser runs while `this` is still the throwaway class instance — so an arrow created there mutates an object nothing renders, and the event silently does nothing. In `created()` the proxy already exists and the closure captures it.

- ❌ An arrow in a field initialiser (`private readonly onX = () => this.doX()`) — captures the wrong `this`, see above.
- ❌ An inline arrow in `registerHandler` — it can never be unregistered.
- ❌ Passing `this.methodName` bare — the bus calls handlers with its own context and `this` is lost.
- ❌ Subscribing in a store's `setup()` — it runs on every resolution of the store and piles up duplicates.

## Testing (`frontend/test/`)

Vitest. Every spec lives under `frontend/test/`, grouped by the layer it exercises, named `{subject}.spec.ts`:

```
frontend/test/
  setup.ts          reflect-metadata, pinia, jsdom shims
  support/          test doubles (MemoryFileTransport)
  domain/           entities, catalogues, type identity
  services/{domain}/  application services — mirroring their folder in src/
  services/         validators
  handlers/         event subscribers
  infrastructure/   transports, queries, event bus
  store/            Pinia stores
```

1. **Location and name.** A spec for code in `src/{layer}/…` goes in `test/{layer}/`. No `*.test.ts`, no specs under `src/`.
2. **Every new class in `domain/`, `application/`, `infrastructure/` and `store/` ships with a spec.** Components are tested only when they carry non-trivial logic.
3. **Mock at the boundary, not the unit.** There are two boundaries: the generated bindings (`bindings/**`) for the transport itself and for end-to-end cases, and the transport (`MemoryFileTransport`) for queries and everything above. Whatever sits between them stays real. A test that mocks the very thing it checks proves nothing.
4. **Singletons are resolved once per file.** Stores and handlers are singletons; resolving them per test leaves a handler subscribed to a stale bus. Resolve at module level and reset state in `beforeEach`.
5. **Run** with `npm test` (`vitest run`) or `npm run test:watch`.
6. `vitest.config.ts` must keep `useDefineForClassFields: false` and `experimentalDecorators: true` — both DI and entities depend on them.

## General conventions

### Language

- **Everything in this repository is English.** Code, names, comments, documentation, commit messages — and user-facing text too: template labels, route titles, error and toast messages, validation texts.
- **i18n is wired but optional.** `vue-i18n` is initialised in `AppBootstrap` with the `en` locale and `src/locales/en.json` is deliberately empty. Write strings straight into templates; do not convert them into `$t()` keys without being asked.

### Third-party libraries

They are allowed, but **ask the repository owner before installing a new dependency** — what it is and what it is for. This covers UI libraries and utilities alike.

### Naming

| Artifact | Convention | Example |
|---|---|---|
| Class | `PascalCase` | `ItemStore` |
| Entity | `PascalCase` + `Entity` suffix | `ItemEntity` |
| Event handler | `PascalCase` + `Handler` suffix | `ErrorHandler` |
| Type | `T` prefix + `PascalCase` | `TItemStatus`, `TItemDraft` |
| Interface | `I` prefix + `PascalCase` | `IDropHandler` |
| Vue component file | `PascalCase.vue` | `ItemCard.vue` |
| Vue component in a template | `kebab-case` | `<item-card />` |

This applies to everything under `src/` **except**:
- `src/views/` — keep the existing naming (kebab-case folders, `index.vue`, `*.route.ts`);
- files at the root of `src/`.

**Every file is named exactly after the class it holds — services included.** There is no
`{name}.service.ts` form: the class is `ToastService`, so the file is `ToastService.ts`. The `Service`
suffix on the class name is mandatory (see **Services**).

### Interfaces vs types

`interface` is a behavioural contract a class implements — methods, not just fields:

```ts
export interface IDropHandler {
    canHandle(event: DragEvent): boolean
    handle(event: DragEvent): Promise<void>
}
```

`type` is a data shape: structures, unions, mapped types, aliases.

```ts
export type TItemStatus = 'draft' | 'active' | 'archived'
export type TValidationResult = { valid: boolean; errors: Record<string, string> }
```

**Never use `interface` where `type` would do** — that is, when it only describes fields and no class implements it.

### No standalone functions — OOP only

**`export function` is forbidden.** All logic lives in a class as a method.

- ✅ `class StringUtils { static truncate(...) {} }`
- ✅ `class FormatterService { format(...) {} }`
- ❌ `export function truncate(...)`
- ❌ `export const helper = () => ...`

This applies everywhere: services, stores, utilities, helpers. The only exception is a decorator factory (`@RoutePage`, `@RouteTitle`, `@InjectableStore`) — TypeScript's syntax requires a callable. Do not extend the exception to anything else.

Local arrow helpers and fixtures inside a spec file are fine.

### One artifact per file

- **One class per file.** Never two classes in one `.ts`.
- **One type per file** — `T{Name}.ts`, except types that have no meaning apart from each other (a request/response pair of one operation).
- **One component per file.**

## Domain layer (`src/domain/`)

Entities, events, errors and pure helpers. Framework-free: no Vue, no tsyringe, no bindings, no IO; the only external dependencies are `@iappx/entity-repo` and `@iappx/entity-repo-query`.

- **Entities** — `entities/{feature}/`, rules under **Data**.
- **Filter rules** — static methods returning a filter node, next to the entity they belong to. They are domain knowledge ("an active account"), not query plumbing.
- **Models that are not entities** (`MenuItem`, `AppTheme`) — `models/`. Immutable structures with no data source behind them.
- **Events** — `events/{area}/`, one class per file.
- **Errors** — `errors/`.
- **Helpers** — static methods on a class, never module-level functions.
- **Barrels (`index.ts`)** in a feature folder keep imports short: `@/domain/entities/item`. New file — add it to the barrel.
- Imports always go through the `@/` alias, never relative paths across folders.

### No mock data

Invented data must not exist at runtime. Catalogues in `domain/` are real lookups with no made-up values; data comes from live sources. Fixtures live in `frontend/test/`, never in `src/`.

## Vue components (`src/components/`, `src/containers/`, `src/views/`)

### Key principle

**All components are classes**, via `@iappx/vue-facing-di`. The Composition API (`<script setup>`, `defineComponent`, `ref`, `reactive`) is **never used**.

### ⚠️ Extract early

**Any distinct piece of UI belongs in its own component.** Do not wait for a template to grow:

- the block has its own state, loading flag or lifecycle logic;
- the block can be named with a noun: `ItemCard`, `CommentForm`, `EmptyState`;
- the block repeats inside a `v-for` — extract it immediately;
- the block is shown by `v-if` and its content is non-trivial;
- the parent template exceeds ~30 lines of meaningful markup.

Too many components beats too few. A component used exactly once is still the right call.

### File shape

```vue
<template>
  <!-- ... -->
</template>

<script lang="ts">
import { Component, VueBase } from '@iappx/vue-facing-di'

@Component({})
export default class MyComponent extends VueBase {
}
</script>
```

| Mechanism | How |
|---|---|
| Component options | `@Component({ components, emits, directives })` |
| Props | `@Prop({ required: true })` on a `public readonly` field |
| v-model | `@VModel()` |
| Watchers | `@Watch('prop')` above the method |
| Local state | plain public class fields with initialisers |
| Computed | `get` accessors |
| Methods | plain methods; `public` when called from the template |
| Lifecycle | `created()`, `mounted()`, `beforeUnmount()` — may be `async` |
| Emitting | `this.$emit('close')` |
| Navigation | `this.$router.push('/path')` |

### Dependency injection

Services and stores are injected in the constructor via `@inject(Token)` from `tsyringe`, and `super()` is always called. Use `public readonly` when the template needs it. No dependencies — no constructor.

```ts
constructor(
  @inject(ItemStore) public readonly itemStore: ItemStore,
  @inject(EventBus) private readonly eventBus: EventBus,
) {
  super()
}
```

### Route parameters

**URL parameters are read through `this.$route.params`, never through `@Prop`:**

```ts
// ✅
const id = this.$route.params.itemId as string

// ❌ @Prop() is input from a parent component, not a segment of the address
```

`@PropsRoute()` on a route class is a different thing: it declares that the route has parameters in its URL, and it is required for such routes. It has nothing to do with component `@Prop`.

### Global modals

A modal opened from more than one place is mounted **once** in `components/app/AppModals.vue` and opened by an event on the bus — never duplicated in every page that can open it.

### Imports

- Decorators and base class — `@iappx/vue-facing-di`
- DI — `tsyringe`
- Everything internal — through `@/` aliases; relative paths only to `bindings/`, which sits outside `src/`

## Forms and validation

1. **A form edits a draft, not an entity.** The component keeps the fields in its own state and assembles a `T{Name}Draft`; entities are created and changed by a service only.
2. **Validation is a class of its own** under `application/validators/`, `@injectable()`, with `validate(draft): TValidationResult`. No validation in a template, and none in component methods beyond calling the validator.
3. **The result is a `TValidationResult`** (`{ valid, errors }`) where `errors` maps field to message. Collect every problem in one pass, not just the first.
4. **Knowledge of allowed values stays in the domain** — the validator asks the catalogue (`ItemStatusCatalog.has(...)`) instead of keeping its own list.
5. **Field markup is `UiFormField`**: it provides the `<label for>`, a slot with `fieldId`/`describedBy`, and the error text. Form fields are not hand-rolled.
6. **Submission state** is a flag on the component; buttons are disabled while the operation runs (`:loading` on `UiModal`).
7. **The form does not display operation failures** — they travel through the mechanism in **Errors**.
8. A third-party validation library (zod, vee-validate, …) requires the repository owner's approval.

## Accessibility — the mandatory minimum

Full WCAG compliance is not required. What follows is, because without it the interface is simply broken:

1. **Semantics.** Anything clickable is a `<button type="button">`, not a `<div @click>`. Links are `<a>` / `router-link`.
2. **Keyboard.** A modal closes on Escape, focus moves inside when it opens and returns to the previous element when it closes. Both shells (`UiModal`, `ConfirmDialog`) inherit this from `ModalShellBase`; a new shell does too.
3. **Icon buttons have a name.** A button without text carries an `aria-label` (`title` in addition, not instead).
4. **Visible focus.** The global `:focus-visible` rule in `index.css` is never removed; if you override `outline`, provide a replacement.
5. **Labelled fields.** `<label for>` is bound to the field `id` — through `UiFormField`. Errors are tied to the field with `aria-describedby` and flagged with `aria-invalid`.
6. **`alt` on images** that carry meaning.
7. **Dialogs carry a role**: `role="dialog"` (or `alertdialog`) plus `aria-modal="true"` and `aria-labelledby`.

Screen-reader support, `aria-live` regions and WCAG contrast checks are **not required** unless asked for.

## Pages and routing (`src/views/`)

### Files per page

```
src/views/app/items/
├── index.vue            page component
└── items.route.ts       route class
```

Child pages nest inside the parent folder. Routes are discovered automatically — `src/router.ts` globs `./views/**/*route.ts`, so nothing needs registering.

The page class is named `{Name}Page` and follows every Vue component rule.

### Route class

```ts
@RoutePage(() => import('./index.vue'), 'items', () => AppRoute)
@MenuIncluded(1)
@RouteTitle('Records')
@RouteIcon(Box)
export class ItemsRoute extends RouteBase {
}
```

A plain TypeScript class (no Vue), file in `kebab-case` matching the page folder, base class `RouteBase`. A desktop app has no login wall, so there is no authorised route base; if a project needs gated sections, add a base class in `lib/router/base/` — never a check inside the page.

Decorators from `@/lib/router/decorators/RouterDecorators`:

| Decorator | Purpose |
|---|---|
| `@RoutePage(component, path, parent?)` | required; lazy import, path segment, lazy parent getter |
| `@RouteRedirect(to)` | redirect for shell routes with no content of their own |
| `@PropsRoute()` | declares that the route carries URL parameters |
| `@RouteTitle(title)` | static title |
| `@RouteIcon(icon)` | menu icon, a `@lucide/vue` component |
| `@MenuIncluded(order?)` | include in the sidebar |
| `@RouteMeta(data)` | arbitrary metadata; prefer the specific decorators |

A title that depends on a loaded entity comes from overriding `getRouteTitle`. Stores are reached with `container.resolve(...)` there: a route class is not a component and has no constructor injection.

## Services (`src/application/`, `src/infrastructure/`)

### When to create one

Anything that is not UI state belongs in a service (or a store). Use a service when the logic need not be reactive or shared between components; when it wraps a library or a platform capability; when it is a reusable operation; when it coordinates several other services.

### Shape

A plain class decorated with `@injectable()` or `@singleton()` from `tsyringe`. No Vue, no `StoreBase`.

| Decorator | Lifetime | When |
|---|---|---|
| `@injectable()` | new instance per resolution | default: stateless services |
| `@singleton()` | one per app | when it holds its own state: `EventBus`, transports, `ToastService`, every handler |

> ⚠️ **`@inject(Token)` on every constructor parameter is mandatory.** Do not rely on reflection: a bare parameter is a defect even where it happens to resolve. Same rule for services, transports, handlers and stores.

### Registration — no manual wiring

`@injectable()` / `@singleton()` register the class when its module is imported, and `@inject` resolves the graph. **Never add manual `registerInstance`/`new` wiring** — add a decorator instead. The single exception is the router instance in `AppBootstrap`, registered under `DiTokens.Router` because vue-router creates it.

### Stores in services, and pinia ordering

A store only exists after `app.use(pinia)`. Therefore:

- Constructor injection of a store is for classes created later: the handlers picked up by `AppBootstrap`, and components.
- Everything else resolves a store lazily with `container.resolve(Store)` **inside a method**, never in a constructor.

### Layout — a service is a folder, not a file

**Every service lives in a folder of its own, named after its domain, and everything that belongs
to that service lives inside it.**

```
src/application/services/{domain}/{Domain}Service.ts   use-case service
src/application/handlers/{Name}Handler.ts              event subscriber
src/application/validators/{Name}Validator.ts          validator
src/infrastructure/{area}/{Name}.ts                    adapters, entity-repo, event bus
```

```
src/application/services/item/
    ItemService.ts
    types/
        TItemCreateOptions.ts
    constants/
        ItemLimits.ts
```

1. **Folder name is the domain in `camelCase`, class name is `{Domain}Service` in `PascalCase`**, and
   the file is named exactly after the class: `services/item/ItemService.ts`,
   `services/toast/ToastService.ts`, `services/id/IdService.ts`. One service per folder.
2. **The `Service` suffix is mandatory**, like `Handler` on handlers and `Entity` on entities.
3. **Everything the service owns sits in its folder** — its types, models, constants, enums, helper
   classes and abstract bases, in `types/` / `models/` / `constants/` / `enums/` / `base/`
   subfolders. This mirrors what stores already do (see **Stores → Layout**).
4. ❌ **Nothing that belongs to one service is parked "somewhere general".** A `TItemCreateOptions`
   in a shared `application/types/`, a constant in a global `constants/`, a helper next to an
   unrelated service — all defects. If it exists only for one service, it goes in that service's
   folder; if it turns out that a second service needs it, it belongs to the domain, not to the
   shared bucket — move it to `domain/`.
5. **A type shared by a service and its own store belongs to the service.** `TToast` is used by both
   `ToastService` and `ToastStore`, and it lives in `services/toast/types/` — the store imports it
   from there. The other way round would put an `application` import on a `store` path, and
   dependencies only ever point inwards (see **Architecture — layers**).
6. **A folder is created with the service, not once it grows.** A service with a single file is
   still `services/{domain}/{Domain}Service.ts` — never loose at the root of `services/`.
7. Shared DI tokens, environment config and framework scaffolding stay where they are
   (`config/`, `constants/`, `lib/`) — those belong to no service.

Specs follow the same shape: `test/services/{domain}/{Domain}Service.spec.ts` (see **Testing**).

## Stores (`src/store/`)

| | Service | Store |
|---|---|---|
| State | none (or private) | reactive, shared across components |
| Decorator | `@injectable()` / `@singleton()` | `@InjectableStore` |
| Base class | none | `StoreBase<Self>` or `LoadableItemStoreBase<TItem, Self>` |
| Use when | operations, transforms, side-effects | cached data, global UI state |

### Store shape

```ts
@InjectableStore
export class ItemStore extends LoadableItemStoreBase<ItemEntity, ItemStore> {
    public search = ''

    constructor(
        @inject(ItemService) private readonly itemService: ItemService,
        @inject(EventBus) private readonly eventBus: EventBus,
    ) {
        super()
    }

    public create(draft: TItemDraft): Promise<void> {
        return this.guard('ItemStore.create', async () => {
            const created = await this.itemService.create(draft, Date.now())
            this.items = [...this.items, created]
            this.eventBus.emitEvent(new ItemCreatedEvent(created.id, created.title))
        })
    }

    protected loadItems(): Promise<ItemEntity[]> {
        return this.itemService.getAll()
    }
}
```

- A store owns state and announces what happened. It **does not write to disk, raise toasts, touch `localStorage`, `document` or timers** — services and handlers do.
- Loading a collection goes through `LoadableItemStoreBase`: the subclass implements `loadItems()` against an application service. `updateInterval = 0` (the default) means "load once".
- An action that reaches for data catches the failure and emits `AppErrorEvent`.
- `@InjectableStore` replaces both `@injectable()` and Pinia registration. **Always use it for stores.**
- A store is injected into a component exactly like a service.

### Layout

```
src/store/modules/{storeName}/
    {StoreName}Store.ts
    types/ models/ enums/ constants/
```

Subfolders are named by what they hold. Do not mix files of unrelated stores in one folder.

## Theming and styling

- **All colour comes from CSS variables** in `src/assets/styles/css/index.css`; `:root`/`.light` and `.dark` carry the same token set. Components never hardcode a colour — use the Tailwind aliases (`bg-background`, `text-muted-foreground`, `border-border`, `bg-primary`, …).
- **Which theme to polish is part of the task.** There is no blanket requirement that both themes look equally finished: follow the request, and if it says nothing, ask. Tokens stay mandatory regardless, which is what makes the other theme work anyway.
- **Rebranding is a token change, not a component change** — `--primary` / `--accent` / `--ring` (and their `--sidebar-*` twins) are edited in `index.css` for both themes at once. Never scatter literal `hsl` values through components.
- **Shared primitives** (`.surface`, `.btn-primary`, `.btn-secondary`, `.btn-icon`, `.ui-input`, `.pill`, `.nav-link`) are defined once in `index.css`. Reuse them instead of re-deriving the same Tailwind chain.
- **Focus ring and scrollbars** are set globally in `@layer base` from the same tokens. Do not override them locally.
- The static splash in `frontend/index.html` duplicates `--background` / `--primary` by necessity (it renders before the bundle boots). Keep it in sync.

## Animations

`motion-v` drives element animations. Import `motion` and register the variants you need as named components; use them in `kebab-case`:

```ts
@Component({ components: { MotionDiv: motion.div } })
```

Props: `:initial` (state before entering), `:animate` (target, or an array of keyframes), `:exit` (state when leaving), `:transition` (`duration`, `delay`, `ease`, `repeat`, `repeatType`).

`:exit` only works **inside a `<transition>`** — without one the element is removed instantly and the exit animation never runs. Use `@after-leave` on the `<transition>` to run logic once the exit completes. Do not add CSS transition classes (`.x-leave-active`): `motion-v` drives the animation itself.
